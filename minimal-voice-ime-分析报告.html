01项目定位

一个 只占一条窄语音栏的安卓输入法。按住说话 → 流式出字 → AI 整理 → 点一下发送； 需要手打时按 ABC 展开全键盘（走离线 Rime 拼音）。识别与整理各自提供 云端（阿里云百炼）与本地（sherpa-onnx / llama.cpp）两套完整实现，可整条链路离线。

产品定位清晰且有差异化：核心主张是「省屏幕 + 不打扰」，作者把它定义为「不占屏幕的安卓语音输入法」。 技术上是一个 双引擎（语音 + 拼音）三链路（云端/本地/降级） 的复合型输入法， 难点不在 UI，而在链路编排、状态机与资源生命周期。

04设计亮点

① 候选计算的版本号机制

每轮候选带一个自增 candVersion，任何阶段发现版本不匹配就整体丢弃。 配合 35ms 防抖与单线程池，连续敲键只算最后一串，旧结果绝不会覆盖新结果。

IME.java:1705-1733

② 整理令牌防止幽灵回填

每轮 AI 整理持一个 polishToken。用户中途发送或重新识别时令牌作废， 后台结果回来直接丢弃，不会把整理文本插回已被改动的输入框。

IME.java:2601-2636

③ 失败重试不丢录音

录音 PCM 全程缓存（上限 120 秒），网络失败后点一下中间键即可用缓存音频重转， 无需重新说话。重试时自动从实时 WS 切到整段上传。

IME.java:2236-2299

④ 音节 DP 切分做纠错校验

用 405 个合法音节做动态规划切分，只有能完整切开的纠错变体才被采纳， 避免邻键替换产生垃圾候选。

RimeEngine.java:296-322

⑤ librime 双层纠错

Rime 规则层（spelling_correction / key_correction）+ Java 层（QWERTY 邻键替换、 删位、相邻换位）叠加，覆盖 zh/z、ang/an、n/l 等常见混淆。

pinyin.yaml:130-145

⑥ 专有名词双保险

词表既注入 LLM 的 system prompt 作约束，整理完再用 TermFix 本地做 子串替换与编辑距离校正，保证人名公司名不被改写。

TextPolisher:232 / TermFix:75

05问题与风险

P0API Key 明文存储，且局域网同步明文外传

API Key 明文存于 SharedPreferences（Prefs.java:88），未用 EncryptedSharedPreferences 或 Android Keystore。更严重的是局域网同步的「asr」分组会把 asr_api_key、 polish_key 一起放进 payload，经 无 TLS 的 TCP 明文 发出 （LanSyncManager.java:466/512）。同 WiFi 可被嗅探。

另有 401 错误提示回显 Key 长度与尾号 4 位（BailianAsrEngine.java:300），可被截图。

P0局域网同步存在越权覆盖

接收端完全信任发送方声明的分组，本机勾选不参与校验（Prefs.java:327-352）。 用户一旦点「接收」，对方即可覆盖 asr_endpoint 与 asr_api_key， 把后续所有语音转写与整理请求导向攻击者地址 —— 这是典型的 DNS/端点劫持。 配对码为 4 位且随 UDP announce 明文广播，同网段可直接获取。

P1HttpAsrEngine 缓冲区竞态

feed() 无同步写 buffer，而 finish() 在另一线程并发读 （HttpAsrEngine.java:56-64）。同场景 BailianAsrEngine 已用 synchronized， 说明这是遗漏而非有意为之，会造成丢帧或数组越界。

P1取消后兜底请求仍在上传

RealtimeAsrEngine.fallback() 中的兜底引擎是局部变量 （RealtimeAsrEngine.java:339），父类 cancel() 只关闭 socket。 用户上滑取消后，兜底 HTTP 仍会继续把音频上传完毕。

P1每次录音都新建 OkHttpClient 且从不关闭

四个引擎各自 new OkHttpClient()（Realtime:38 / Bailian:45 / Http:41 / Ws:36）， dispatcher 与连接池从不 shutdown，每次录音泄漏线程。这是长跑场景下的稳定累积型泄漏。

P1整理耗时计算跑在主线程

clean() → TermFix.apply 在主线程执行逐窗口编辑距离校正， 每次都重新分配 DP 矩阵（TermFix.java:115-133）。长文本 + 大词表会掉帧。 tidyPunctuation 的多条正则同样在主线程。

P2rime 模块的 Kotlin 层是完整死代码

Rime.kt / RimeDispatcher.kt / RimeKeyMapper.kt / RimeMessage.kt / X11Keys.kt 互相引用形成闭环，主程序只 import RimeApi 与 RimeCandidate。实际生效的是「Java static + 全局 LOCK」这条并行路径。 X11Keys 的 135 行 keysym 常量因走 simulateKeySequence 完全用不上。 这套协程/Flow 通道还额外拖进了 kotlinx-coroutines 依赖。

P2蓝牙链路整条已停用但留有残迹

MinimalVoiceIME.java:2135 硬编码 boolean bt = false， enterSco / hasBluetoothMic 全项目无调用点。 但 leaveSco 仍在 2388 / 2416 行无条件调用，会把音频模式重置为 MODE_NORMAL。

P2本地模型下载仅校验文件长度

LocalModelManager 只比对文件长度阈值（≥90%，自定义档 ≥98%）， 无 sha256 校验（LocalModelManager.java:150-157）。 截断或被替换的模型文件会被判为就位，仅靠事后 probe() 兜底。 下载源硬编码 hf-mirror 镜像，境外不可用。

P2零测试 + 两个上帝类

无 src/test、无 androidTest、无 CI、无 lint 配置， build.gradle 里连 junit 依赖都没有。而 PhraseParser、PhraseStore.matchIn、 Prefs.addTokens 都是纯逻辑、本可被测。 SettingsActivity 3584 行混合了至少 15 个独立领域；MinimalVoiceIME 2472 行 混合了 IME 生命周期、按键、候选、录音、引擎选择、整理、剪贴板、词库。

P3资产冗余与文档不一致

assets/pinyin_words.txt（464 KB / 25,666 行）全仓无任何代码引用， 已用 grep 确认。README 称其为「辅助简拼」并说「自带 2.5 万词的词表」， 但真正的简拼能力来自 Rime 的 abbreviation 规则，而真实词库是 luna 词典的 43,837 条。 README 同时没有提到 assets/rime 会在首次启动被完整复制到 filesDir（约 6.5 MB）。

P3其他细节

· uploadWithRetry 对 401/400 参数错误也重试一次（BailianAsrEngine.java:147）
· Whisper 分支注释称「language 留空让它自己判」，代码却写死 setLanguage("zh")
· copyAssets 遇已存在非空文件即跳过，应用升级后词库/schema 变更不会生效（RimeEngine.java:94）
· Boost.cmake 的 boost 路径写死 POSIX 绝对路径 /tmp/boostroot，Windows 构建受阻
· librime-predict 走 master.zip 且 sha256 设为 bypass，无校验无版本固定
· AsrConfig.load 中 bailian 分支与 fallthrough 分支代码完全相同（AsrConfig.java:67-77）

06质量指标

工程规范

提交历史清晰，CHANGELOG 逐版本记录到 0.6.60（约 60 个版本）。 迭代节奏密集，每版都有明确的功能或修复目标，作者对细节的打磨程度相当高 （如「读到模型列表时排除 max/pro/plus/turbo 等付费档位」「百炼域名收紧为白名单」）。

短板：零测试、零 CI、零静态检查，没有任何自动化质量闸门。

可维护性

资源与逻辑分离得不错：词库在 assets、配置在 Prefs、 模型在 filesDir。三个 Store 结构完全一致（Gson + filesDir JSON + 静态 cache + 全量重写 + 吞异常）， 可抽 BaseJsonStore。同步的导出/导入是两份平行 if-chain，加键要改两处。

可抽公共层：BaseJsonStore、TokenLedger、DialogBuilder、单例 OkHttpClient。

07改进路线建议

立即处理 · 安全

① API Key 迁入 EncryptedSharedPreferences
② 同步 payload 默认剔除 Key，或改端到端加密
③ 接收端校验发送方声明的分组，不允许越权覆盖
④ 移除 401 提示里的 Key 尾号回显
⑤ 本地模型下载补 sha256

短期 · 稳定性

① HttpAsrEngine buffer 加 synchronized
② 兜底引擎提为字段并在 cancel 中取消
③ 四个引擎共用单例 OkHttpClient，服务销毁时 shutdown
④ TermFix 移到后台线程
⑤ 清理蓝牙残迹与死代码

中期 · 工程化

① 补单元测试（PhraseParser / Prefs / RimeEngine）
② 拆分两个上帝类
③ 抽 BaseJsonStore / TokenLedger / DialogBuilder
④ 加 CI + lint + 混淆规则
⑤ 删 pinyin_words.txt 并订正 README
